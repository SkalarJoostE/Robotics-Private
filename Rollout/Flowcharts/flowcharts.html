What happens behind the screen for each kind of question an engineer asks, step by step, and what a web page where anyone can ask the same questions would need for each one.

What a web version would need

Today an engineer runs these flows in Claude Code on a PC that has the workspace, the VPN, SVN and the log reader. A web page where anyone can ask a question is only a new front door. Behind it, a server still needs the same workspace and the same access, and every answer is paid per conversation through the API.

Good: reading and reasoning that a web chat can answer. Partial: the answer is fine, a person has to approve what is kept. Engineer PC: changes order software or SVN, needs the robot application, or waits on an engineer at every step, so it stays with an engineer.

Already built

  • A working chat engine (lab-chat-poc), in use since July 2026. It uses the same instructions, skills and log reader as Claude Code, so it gives the same answers.
  • Two channels: lab questions about an order, and RB/ES helpdesk tickets.
  • Read-mostly by design: the helpdesk channel never writes to Jira and ends with a draft reply for a person to send.
  • Cost logging per turn, which is where the figures on this page come from.

Still missing for a shared web page

  • The page itself: a place to type a question and upload a log or zip.
  • One always-on server with the workspace, VPN, SVN and the log reader.
  • API billing: a personal subscription cannot be shared, so a shared service runs on an API key.
  • A queue per order: refreshing an order discards local edits, so two people asking about the same order must not run at once.
  • Tighter permissions and agreement with IT on sending customer logs and software to a cloud model.
  • Review at first: an engineer checks answers before the asker sees them, until case types prove reliable.

00

What happens when you ask a question

any question typed into Claude Code, GitHub Copilot or Codex inside the Robotics-AI workspace

Every assistant opens the same instruction file first, so the same question gets the same treatment whichever tool is used. The request is then matched to a skill: a written procedure for that kind of work, with its own scripts and its own rules. Anything that does not match a skill is answered from the instructions, the documentation and the software itself.

Key points

  • The instruction file is the same for all three assistants (CLAUDE.md points at .github/copilot-instructions.md), so behaviour does not depend on which tool someone uses.
  • A skill is chosen from the wording of the request. The engineer does not have to name it.
  • The lab and ticket flows both end up in log analysis when a log is attached; the precedent search hands over to feature implementation once a reference order is chosen.
  • The same house rules hold on every path: software is read only from the workspace (never from an engineer's own C:\SPD_Projects copy), nothing writes to Jira, and nothing is committed to SVN without the engineer saying yes in the conversation.
01

The investigation spine

any investigation, whether it arrives as a lab issue, an RB/ES ticket or a port check

A lab issue, a Jira ticket and a port verification differ only at the start and the end. The middle is always the same seven steps, in the same order. Following them keeps a review to about ten rounds with the assistant instead of thirty-five, which matters because every extra round re-sends the whole conversation and is billed again.

%%{init: {'theme':'base','themeVariables':{'fontFamily':'Nunito Sans, Segoe UI, sans-serif','fontSize':'15px','lineColor':'#47597a','primaryTextColor':'#16233a','textColor':'#16233a','edgeLabelBackground':'#ffffff','clusterBkg':'#f3f5f9','clusterBorder':'#b7cbe9'},'flowchart':{'curve':'basis','htmlLabels':true}}}%%
flowchart TD
    S1[1 Intake<br/>fetch or refresh the order software,<br/>place the log in the order's Log folder]:::script
    S2[2 Prior art<br/>search the case base and the<br/>Template Known Issues page]:::ai
    S2D{Seen before?}:::decision
    S3[3 Pre-generated summaries first<br/>order Profile.md, Sequence CSVs<br/>before any raw XML]:::ai
    S4[4 Log census<br/>four Loupe queries sent together]:::ai
    S5{5 Big search ahead?<br/>more than 5 rounds or 10k of material}:::decision
    SUB[Hand it to a helper agent<br/>that returns only the conclusion]:::ai
    S6[6 Targeted confirmations<br/>one claim per query]:::ai
    S7[7 Write-up]:::ai
    LOGQ{Engineer: log it?}:::human
    CB[(Case base<br/>md documents logs)]:::store

    S1 --> S2 --> S2D
    S2D -->|"Yes: known fix, or<br/>template defect already fixed"| S7
    S2D -->|"No or partly"| S3 --> S4 --> S5
    S5 -->|Yes| SUB --> S6
    S5 -->|No| S6
    S6 --> S7 --> LOGQ
    LOGQ -->|Yes| CB
    CB -.->|next case starts here| S2

    classDef human fill:#fff3db,stroke:#ffa400,color:#16233a

Key points

  • Prior art comes before any new digging. Field issues repeat, and a past write-up is often most of the answer.
  • The order's Profile.md lists its hardware and every application's settings in about 15 KB. Building the same picture from the XML took about five rounds on one review, roughly 80 times the cost.
  • Independent lookups go out together in one round. Lookups that depend on an earlier answer are not merged, so speed never replaces a check.
  • Each resolved case is filed back into the case base, so the next similar case starts with an answer.
02

A lab issue comes in

"99441979 stops after the second sample, here is the log" · "the lab committed again, check it"

A colleague in the lab, or at a customer install, reports a robot problem with an order number and usually a log file. The assistant gets the exact software that robot runs, checks whether the problem is already known, and always ends with a diagnosis or a best hypothesis with its reasoning. It never ends with only a request for more information.

%%{init: {'theme':'base','themeVariables':{'fontFamily':'Nunito Sans, Segoe UI, sans-serif','fontSize':'15px','lineColor':'#47597a','primaryTextColor':'#16233a','textColor':'#16233a','edgeLabelBackground':'#ffffff','clusterBkg':'#f3f5f9','clusterBorder':'#b7cbe9'},'flowchart':{'curve':'basis','htmlLabels':true}}}%%

    ASK -->|No| CLAR[Ask for what is missing]:::human --> SRC
    ASK -->|Yes| SRC{Where is the software?}:::decision

    SRC -->|On SVN| VPN{SVN reachable?}:::decision
    VPN -->|"No: VPN off"| STOP1[Stop: ask the engineer<br/>to connect the VPN]:::rule
    VPN -->|Yes| CO{Already checked out?}:::decision
    CO -->|Yes| REF["Refresh in place<br/>fetch-project.ps1<br/>logs are kept"]:::script
    CO -->|No| NEW["Check out the order<br/>fetch-project.ps1"]:::script
    SRC -->|"Customer zip"| ZIP["Install the zip as its own folder<br/>Process-SoftwareFolder.ps1<br/>never mixed with SVN"]:::script

    PLACE --> PRIOR["One batch of lookups<br/>case base, Template Known Issues,<br/>order Profile.md"]:::ai
    PRIOR --> HASLOG{Log provided?}:::decision
    HASLOG -->|Yes| LOGA[[Log analysis flow]]:::ai
    HASLOG -->|No| SOFT[Reason from the software alone<br/>sequences, tables, action code]:::ai

    DIAG --> FIX{Change needed?}:::decision
    FIX -->|Yes| IMPL[[Feature implementation flow]]:::ai
    FIX -->|No| DONE
    IMPL --> DONE{Fix confirmed<br/>on the robot?}:::human
    DONE -->|Yes| LOGIT[Offer: log this lab resolution]:::ai

Key points

  • The software is always the exact version under investigation: refreshed from SVN, or installed from the customer's zip. If SVN cannot be reached the assistant stops instead of using another copy.
  • A refresh never deletes the order folder, so logs and notes stay where they were.
  • When the lab says "we committed again" or "here is a new zip", the same step runs again and everything read earlier is treated as out of date.
  • No log is not a dead end. The assistant answers from the software and says which log would settle what is still open.
  • The resolution is filed only after the fix has been confirmed on the robot.

03

Reading a robot log

"why did this run hang?" · "what went wrong in this .glf?"

The robot writes binary .glf log files that can hold hundreds of thousands of lines. The assistant never reads them as text. It asks questions through a dedicated log reader (the Loupe server), starting with a fixed overview and then narrowing one question at a time, so that only the lines that matter end up in front of it.

%%{init: {'theme':'base','themeVariables':{'fontFamily':'Nunito Sans, Segoe UI, sans-serif','fontSize':'15px','lineColor':'#47597a','primaryTextColor':'#16233a','textColor':'#16233a','edgeLabelBackground':'#ffffff','clusterBkg':'#f3f5f9','clusterBorder':'#b7cbe9'},'flowchart':{'curve':'basis','htmlLabels':true}}}%%
flowchart TD
    Q([Log file handed over]):::start --> MCP{Log reader<br/>available?}:::decision
    MCP -->|No| STOP[Stop and explain how to start it<br/>no workaround, no manual reading]:::rule
    MCP -->|Yes| OPEN["Opening batch, four questions at once<br/>run summary, crashes,<br/>error census, activity timeline"]:::ai
    OPEN --> KIND{What kind of problem?}:::decision
    KIND -->|"Something failed"| CENSUS[Group errors by type]:::ai
    KIND -->|"Did X happen, when?"| TEXT[Search for that event]:::ai
    KIND -->|"Hang or freeze"| HANG[Timeline gaps<br/>and threads]:::ai
    KIND -->|"What led up to it?"| AROUND[Read the lines<br/>around one moment]:::ai
    CENSUS & TEXT & HANG & AROUND --> NARROW[Narrow down<br/>each question smaller than the last,<br/>an empty answer is a finding]:::ai
    NARROW --> SAMPLE[Follow the affected sample<br/>by rack position]:::ai
    SAMPLE --> NOISE["Set aside known false alarms<br/>look up error codes in this<br/>order's own error table"]:::ai
    NOISE --> HOST{Problem in the PC<br/>application itself?}:::decision
    HOST -->|Yes| HL[Ask the engineer for<br/>the separate host log]:::human --> REPORT
    HOST -->|No| REPORT[Report<br/>summary, timeline, root cause,<br/>affected samples, recommendation]:::ai

Key points

  • Without the log reader there is no analysis. The assistant stops and says how to fix it rather than guessing from the raw file.
  • The four opening questions always go out together, which turns several rounds into one.
  • Searches are capped at 20 to 30 results and never paged through. A wide search fills the conversation with lines that are then re-sent on every later round.
  • Error codes differ per robot, so a code is looked up in that order's own error table, never in a template or another order.
  • A "COM port opened" line without a reply points to cabling or power, so the assistant stops looking at code there.

For a web version

Good Read only from start to finish; the user uploads a log and gets a report.

04

Solving an RB or ES ticket

"solve RB-380" · "investigate ES-212"

Service tickets from the Robot Aftersales (RB) and Escalation (ES) boards are pulled into a local folder by a scraper script: the ticket text, every attachment, the order's SVN software and, when the customer sent it, their own running software. The assistant diagnoses from that folder and writes an analysis with a draft reply. It never writes to Jira; the engineer decides what to post.

%%{init: {'theme':'base','themeVariables':{'fontFamily':'Nunito Sans, Segoe UI, sans-serif','fontSize':'15px','lineColor':'#47597a','primaryTextColor':'#16233a','textColor':'#16233a','edgeLabelBackground':'#ffffff','clusterBkg':'#f3f5f9','clusterBorder':'#b7cbe9'},'flowchart':{'curve':'basis','htmlLabels':true}}}%%

    SCRAPE --> OK{Download worked?}:::decision
    OK -->|No| STOP1[Stop and report<br/>never diagnose from an old copy]:::rule
    OK -->|Yes| FOLDER[("Service Items folder<br/>ticket text, attachments, SVN software,<br/>customer software, logs")]:::store
    FOLDER --> READ[Read the ticket<br/>and the attachment list]:::ai
    READ --> SW{Which software<br/>is the evidence?}:::decision
    SW -->|"Customer zip attached"| CUST[Customer's software is the source<br/>SVN only for comparison]:::ai
    SW -->|"Ticket links a zip the<br/>scraper could not fetch"| DL[Engineer downloads it<br/>into the ticket folder]:::human --> INST["Install it<br/>Process-SoftwareFolder.ps1"]:::script --> CUST

    CUST & SVNSW --> PRIOR[Search the case base<br/>re-check any match against this ticket]:::ai
    PRIOR --> ROUTE{What does it need?}:::decision
    ROUTE -->|Log| LOGA[[Log analysis flow]]:::ai
    ROUTE -->|Code| CODE[Action code reference]:::ai

05

Have we built this before?

"have we ever built a robot that rinses the probe with KCl between samples?" · "find a reference order for a dual EC flowcell"

Most special requests (B-features) have been built for some earlier customer. The workspace keeps a searchable index card for every delivered order (about 1,275) and a growing collection of feature dossiers. The assistant searches those, the engineer picks the right reference order, and the assistant turns it into a dossier that says exactly what to copy and what not to.

  • Nothing is downloaded until the engineer has chosen the reference order. The index cards are enough to shortlist.
  • The engineer verifies the choice outside the tooling, for example from photos of the built system or by opening its software.
  • The dossier records what not to copy as well as what to copy: a reference order also carries other customer-specific parts.
  • Dossiers grow from live work. Each port adds or updates one, and it becomes "verified" once the first port passes FAT.
  • The interview step is optional and only starts when an engineer asks for it.

06

Building a feature into an order

"port the KCl rinse from 99412345 into 99446390" · "add a setting to switch the sprayer off"

A robot's behaviour lives in XML tables (sequences, settings, positions) and in C# action code stored inside those XML files. The assistant changes both through workspace scripts, checks that every new movement has a position to go to, and builds the code. The final build in the real application and the test on the robot stay with the engineer.

%%{init: {'theme':'base','themeVariables':{'fontFamily':'Nunito Sans, Segoe UI, sans-serif','fontSize':'15px','lineColor':'#47597a','primaryTextColor':'#16233a','textColor':'#16233a','edgeLabelBackground':'#ffffff','clusterBkg':'#f3f5f9','clusterBorder':'#b7cbe9'},'flowchart':{'curve':'basis','htmlLabels':true}}}%%
flowchart TD
    Q([Port list from a dossier,<br/>or a direct feature request]):::start --> MIRROR["Refresh the C# code mirror<br/>of both orders<br/>Process-SoftwareFolder.ps1"]:::script
    MIRROR --> DIFF[Compare every code location<br/>between reference and target]:::ai
    DIFF --> SORT{Each difference}:::decision
    SORT -->|"Part of this feature"| PORT[Port it]:::ai
    SORT -->|"Another customer's extra"| SKIP[Leave it out]:::ai
    PORT --> TABLES[Edit the tables<br/>sequences, settings in all three places,<br/>dropdown values, positions]:::ai
    PORT --> CODE["Edit the action code<br/>Sync-ActionCode.ps1<br/>extract, edit, write back"]:::script
    PORT --> TRAYS["Racks and layout if needed<br/>Add-TrayType / Set-TrayLayout<br/>dry run first"]:::script
    TABLES & CODE & TRAYS --> GEO["Check every new step has a position<br/>Check-ManipulatorGeometry.ps1"]:::script
    GEO --> MISS{Position missing?}:::decision
    MISS -->|Yes| ADDROW[Add the position row<br/>the lab teaches the real value]:::ai --> GEO
    MISS -->|No| VERIFY[Regenerate the mirror, re-compare,<br/>compile, run the checklist]:::ai
    VERIFY --> BUILD{Engineer presses Build<br/>in the application}:::human
    BUILD --> TEST[Optional: unattended test run<br/>in emulation, no hardware]:::script
    TEST --> FAT{Lab test / FAT}:::human
    FAT --> COMMIT{Engineer: commit to SVN?}:::human
    COMMIT -->|Yes| SVN[(SVN)]:::store

How answers become knowledge

"wrap up" · "log this ticket resolution" · "add this to the feature catalogue"

The workspace improves because finished work is written down where the next question will find it. At the end of a case the assistant proposes what to keep and where, the engineer approves the list, and the write-up goes into the matching log. Every investigation flow starts by searching those same logs.
