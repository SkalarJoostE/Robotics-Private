### 2.3 The constraint is the search, not only the wait — **CORRECTED 2026-08-20**

Your note: *"Waiting is not the real only constraint. Lab finds a problem, tries to find it
themselves first. Doesn't maybe know its software. After that tries to find what went wrong with
setup, settings etc. That's when they decide, I actually don't know, and come and ask me... It's
not just waiting. It's searching for the problem. It's the same for me."*

This was a real weakness. "Waiting" only counts the queue — the visible, and probably smaller,
half. The cost that never appeared anywhere in the deck is the **search Lab does before anyone is
asked**, and then the *same search* being repeated from scratch by the engineer. Both halves
shrink, and the second one often stops being needed at all.

| Where | Was | Now |
|---|---|---|
| Full, slide 2 body | *"So Helpdesk and Lab wait, and Software Engineering spends its time re-deriving answers..."* | *"**So the search happens twice.** Lab looks first — setup, settings, software they may not know — and only asks when that fails. Then an engineer starts the same search again..."* |
| Full, slide 2 kicker under the quote | *"waiting is the constraint"* | *"the **search** costs more than the answer — for them and for us"* |
| Full, slide 9 card 3 | *"How long they used to **wait** for an answer..."* | *"How long it used to take them to **reach** an answer — searching first, then asking — against how long it takes now."* |
| Short, slide 2 | 4 bullets ending *"So Helpdesk and Lab wait"* | a 5-step numbered chain that walks the actual sequence — see the note below the table |
| Short, slide 2 quote card | *"Waiting is the constraint. For them and for us."* | **"Not just waiting. The same search, twice."** |

Both decks' slide-2 notes now carry a `SAY THE SEARCH PART OUT LOUD` / `WALK THE FIVE STEPS`
block, because this is the half a room will not think of by itself.

**Follow-up, same day — the bullets became a numbered chain.** Your read: *"slide 2 reads a bit
weird with those bullet points. Because of the bulletpoints I think its separate things, but it
actually reads as a continuation."* Correct, and it was a formatting mistake rather than a wording
one: bullets signal *parallel, independent items*, which is exactly what these are not. They are
one story with a beginning and an end. The short deck's slide 2 is now a **numbered chain** —
dots on a vertical rail, so the sequence is carried by the layout:

1. Something goes wrong on a robot
2. Lab starts looking themselves
3. Setup? Settings? The software?
4. Still stuck — so they ask us
5. **And the engineer starts the same search over**

Step 5 gets the Tuscan Sun dot and bold text: it is where the search restarts, and it is the
thing the quote card next to it names. If the steps are ever re-edited, keep them under about
48 characters or they wrap and the rail stops lining up.

## 6. Known issues in the underlying data (found while doing this)

Not blocking the deck, but they affect any figure re-derived later.

1. **The chat cost log double-counts on recent chats.** In the three most recent conversations
   the `api_cost_*` column records a **running session total** rather than that turn's cost,
   so `cost_report.py:143` (which sums the column) over-reports. This is what made chat 14's
   wrap-up look like it cost €4.38 for writing one file — it actually cost about €0.94.
   Everything in the deck was recomputed from token counts instead, which is unaffected.
2. ~~**€3.91 per conversation is stale.**~~ **Fixed 2026-08-19.** The figure is **€4.44** (service
   ticket €6.23, lab question €3.73), recomputed from token counts. Updated in `PROJECT.md` and
   `Access-and-Feedback-Loop.md`; the two dated §8 decision entries keep €3.91 with a supersession
   pointer, because a decision log records what was believed at the time.
3. ~~**`PROJECT.md` contradicts itself on the case count.**~~ **Fixed 2026-08-19** — §2 now reads
   **51 write-ups** with the full category breakdown.
4. **Concurrent chats contaminate the measured window percentages.** You spotted this — it is
   real, and it is why the deck's plan figures come from the *fitted* calibration
   (`plan_calibration.json`), which works from per-turn token counts and is immune to it.

Item 1 is the only one still open — fix the logger before anyone re-runs `cost_report.py`.

**Also settled 2026-08-19:** `PROJECT.md` §3 said *"Helpdesk goes first, alone"*, which the deck
now contradicts. Reversed to **Lab goes first** and recorded as a dated §8 entry, with §4 phases B
and D updated to match. The one-pilot-at-a-time rule is unchanged; only the order flipped.

## 9. The short deck would not open in PowerPoint — fixed at source

**Symptom (2026-08-20):** `Robotics-AI Capability Overview (Short).pptx` opened fine in
LibreOffice but PowerPoint refused it. Re-saving it through LibreOffice cleared it.

**Cause:** seven shapes carried `<a:ext cy="-100584"/>` — a **negative height**, which is invalid
OOXML (`cy` must be a positive coordinate). PowerPoint rejects the file outright; LibreOffice
tolerates it and silently normalises it on export, which is why the re-save appeared to "fix" it.

It came from `numberCard`, which always drew a body text box sized `h: o.h - 2.06`. The short deck
passes `body: ""` on slides 5 and 9, and those cards were shrunk to `h: 1.95` to remove the dead
space underneath — so the box computed to **−0.11 in**. Slide 10's cards are 2.35, which is
exactly why 7 shapes broke and not 9.

**Fixed in both builders:**

1. `numberCard` no longer draws a body box when there is no body text, and clamps the height with
   `Math.max(0.2, o.h - 2.06)` so it can never go negative again. This also removed 7 empty text
   frames that had no business being in the file.
2. Every build now ends with `assertOpensInPowerPoint()`, which reads the written `.pptx` back and
   **throws** if any slide contains a negative `cx`/`cy`, naming the slide and the shape. Verified
   by deliberately re-introducing the bug: the build fails with
   `Invalid geometry — PowerPoint would refuse this file (1 shapes): slide5.xml …`.

**Why the check had to be added.** A LibreOffice render cannot catch this class of bug — it draws
the broken file happily, so both the PDF and the PNG proofs looked perfect. The XML is the only
place the fault is visible, so the gate belongs in the build rather than in the eyeballs.

> **Use the freshly built file, not the LibreOffice re-save.** The re-save is valid but it has been
> through a foreign renderer, which shifts fonts, shadows and spacing. `(Short).pptx` has been
> rebuilt from source and is now correct as generated — the re-saved copy can be deleted.

`build-capability-deck-nl.js` still carries the old `numberCard` and no validator. It is parked and
out of date anyway (§8); if it is ever revived, port both fixes across first.
