What the AI can do

These are skills the AI assistant loads on demand. You describe a problem in plain words; it does the technical legwork — reading logs, pulling software, comparing versions, tracing the robot's program — and reports back.

Diagnose a robot from its logs

Robot log files are a binary format that normally needs a special viewer. The AI reads them directly and explains — in plain terms — what went wrong: the crash, the freeze, the failed sample, and the exact step it happened on.

Helpdesk · Lab · Engineering Loupe log analysis

Solve a service ticket (RB / ES)

Give it a ticket number. It pulls the ticket, the customer's software and logs, and checks what we've solved before. If that's not enough, it reads the logs itself and traces through the robot's actual step-by-step program to find where it broke — then reports a diagnosis with a recommended fix.

How it works

Where the knowledge comes from

The AI itself is a general-purpose assistant with no built-in knowledge of our robots. The expertise is ours: written down as plain text files that live inside the project and get handed to the AI at the right moment. It works in three layers.

1Always on

The ground rules

One core instruction file loads at the start of every conversation. It describes our products, how the robot software is built, our naming, where things live, and which tool to use for what. So from the very first message, the assistant already "speaks Skalar."

2Opened on demand

The playbooks ("skills")

For each bigger job — analyse a log, solve a ticket, implement a feature — there's a written step-by-step procedure. The AI opens only the one that matches the task, so it follows our exact method instead of improvising. A shelf of standard operating procedures it reaches for when relevant.

3Read when needed

The knowledge base

The instructions, the skills, the template docs, the error-code tables and every solved-case write-up are all just plain text files (.md) stored with the project. When the AI needs a fact, it opens the relevant file — exactly like a colleague would. Nothing is hidden or locked away.

In short: the intelligence is off-the-shelf; the expertise is ours — readable, editable text we own and keep adding to. Improving the assistant doesn't mean retraining anything, and it isn't tied to one vendor: it means writing another document. Because it all lives in one place, every assistant and every PC gets the same knowledge automatically.

The foundation

Why it keeps getting better

Three things sit underneath everything above and are the real reason this is worth making official.

Self-improving memory

A growing case base

Every problem we solve gets written up — the symptom, the cause, the fix — and the AI checks it before diagnosing the next one. Field issues repeat, so a past write-up is often most of the answer.

  • 30+ documented resolutions today, across service issues, orders, template bugs and new features
  • Each solved case makes the next diagnosis faster and more accurate
  • Knowledge stops living in one person's head
Live integrations

Connected to the tools we already use

It reads directly from our real systems — no copy-pasting, no exporting.

  • Loupe — the only way to read the robots' binary log files; the AI uses it to explain crashes and hangs
  • Atlassian — reads Jira tickets (RB & ES) and our Confluence setup guides directly
Write once, works everywhere

One shared brain across three assistants and every PC

All the knowledge and skills above live in one place in the project. Whether a colleague uses Claude Code, GitHub Copilot, or Codex — at work or at home — they get the exact same capabilities. Adding a department doesn't mean rebuilding anything; it means giving people access.
